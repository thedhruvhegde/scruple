Methodology

  • Every scenario is a synthetic case generated by the scruple simulator from (environment, seed, case type). The plan fixes the scenarios, their run order and a salted commitment to each hidden ground truth before any agent runs, so the bank cannot be tuned to after the fact.
  • The agent sees only what a real operator would: the case view, tool results and its instructions. It never sees the ground truth or its score.
  • Grading never reads what the agent says about its run. The calls the agent made are replayed through a fresh episode and scored by the environment's versioned verifiers (ledger invariants, hash-chained trace, process, deadlines, self-report, scope). A failed hard check fails the gate; reward is 0 on a failed gate.
  • Pass rates carry 95% Wilson intervals; mean rewards and paired differences carry 95% percentile bootstrap intervals (2,000 resamples, seed 0).
  • The release recommendation uses anytime-valid betting e-processes (the same statistics as the scruple deployment gate) read in the plan's outcome-blind order, so it stays valid if more scenarios are added.

Limitations

  • All cases are synthetic. The results measure the agent's behaviour on the scruple simulator, not real-world outcomes; the simulated counterparties (issuers, banks, merchants) follow modelled assumptions.
  • A run on a subset of the plan describes that subset; slices with small n have wide intervals and should be read as indicative.
  • API agents are run at temperature 0 with the provider's best-effort sampling seed; providers do not guarantee determinism, so a rerun can differ.
  • Provider limits shape API runs: a request over the provider's per-minute input limit has its oldest tool outputs elided (counted under Operations), and a request the provider refuses outright ends the episode.
