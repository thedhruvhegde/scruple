# Performance: dispute generator (roadmap 038)

Synthetic data only. Every number below was measured on the build container with
`uv run python scripts/bench_sim.py --repeats 5` (best of 5 runs, 20,000 cases, seed 7)
and pasted verbatim. They are local wall-clock measurements, not performance claims.

Machine: 4 vCPU "Intel(R) Xeon(R) Processor @ 2.30GHz", Python 3.12.3, pydantic 2.14.3.
**The machine was shared**: other agents ran test suites at the same time (load average
2.9 before the run, 7.7 at the end), so the multi-process rows in particular are noisy
and lower than an idle machine would give. Re-run the script to check.

## Result

Target: at least 10,000 cases per second. Met by the serial generator for every mix
(12.0k to 16.9k cases/s), so no parallelism is needed to reach it.

```
scruple sim bench (synthetic, seed 7, 20,000 cases, best of 5, python 3.12.3, 4 cpus)
serial   default           1180.9 ms      16,936 cases/s
serial   full (d=0.5)      1593.2 ms      12,553 cases/s
serial   hard (d=1.0)      1670.8 ms      11,971 cases/s
sharded  full, 1 worker(s)    1606.2 ms      12,451 cases/s
sharded  full, 2 worker(s)    1946.0 ms      10,278 cases/s
sharded  full, 4 worker(s)    1912.5 ms      10,457 cases/s
in-worker full, 1 worker(s)    6512.4 ms      12,284 cases/s  (80,000 cases kept in the workers)
in-worker full, 2 worker(s)    4174.8 ms      19,163 cases/s  (80,000 cases kept in the workers)
in-worker full, 4 worker(s)    4007.7 ms      19,962 cases/s  (80,000 cases kept in the workers)
```

Before the 038 changes (the parent commit, same script, serial rows only, measured
twice alternating with the new code under the same load; the new code then gave 12.6k
to 12.9k default and 8.7k to 9.1k full, before the GC change below):

```
serial   default           1712.4 ms      11,680 cases/s
serial   full (d=0.5)      2476.5 ms       8,076 cases/s
serial   hard (d=1.0)      2636.4 ms       7,586 cases/s
```

So the full mix went from about 8.1k to 12.6k cases/s (+55%) and the default mix from
about 11.7k to 16.9k (+45%), single core.

## What changed (found by profiling with cProfile, 10,000 full-mix cases)

| change | why | effect |
|---|---|---|
| pause the cyclic GC inside `generate_cases` (and while `generate_sharded` collects results) | repeated generation-2 collections walk the growing list of models; the cases hold no reference cycles, so refcounting frees them | about 30% at 20,000 cases (9.2k to 13.3k cases/s in an isolated check); the GC is re-enabled on return if it was on |
| `evidence.seal` builds the canonical JSON string directly with the C string escaper `json.encoder.encode_basestring` | `json.dumps(sort_keys=True)` on a small nested dict was the largest single cost (about 25% of the profile) | about 1.7x faster per seal (0.29 s vs 0.49 s per 100,000 calls); a hypothesis test checks it equals `seal_reference` on arbitrary unicode, and it falls back to the reference for non-string input |
| cache `reason_code`, `codes_for` and the card-absent code list | each case scanned the 31-code catalogue several times (validator, properties) | a few percent |
| cumulative weights computed once per call instead of once per case | `random.choices(weights=...)` rebuilds them; `cum_weights=` draws identically | small |

Every generated byte is unchanged: `tests/test_sim_speed.py` pins SHA-256 digests of
9,000 cases per mix (default, full, hard) recorded before the changes.

Tried and dropped: building evidence documents with `model_construct` (skipping
validation). It was not faster: pydantic's `model_construct` is pure Python and cost
about as much as validation in pydantic-core.

## Parallel generation and its limit

`generate_sharded(seed, n, mix, workers=...)` splits the work into shards of 2,000
cases, each from its own derived seed (`shard_seed`), so the output depends only on
`(seed, n, mix, start, shard_size)`, never on the number of workers (tested). It is a
different stream from `generate_cases(seed, n)`.

Returning cases to the calling process does not scale: unpickling a pydantic model runs
`BaseModel.__setstate__` (about 6 microseconds each in a profile, 150,000 models per
20,000 cases), single-threaded in the parent, which costs about as much as generating
them. "sharded" rows are therefore no faster than serial. Keeping each shard in the
worker that generates it ("in-worker", as a training or evaluation pipeline that
consumes cases where they are made would) scales to about 20k cases/s with 4 workers on
this shared machine.

## Not measured

The `DisputeEngine` (event-sourced since 036) was not benchmarked here; `outcome()` and
`ActionResult.entries` scan the whole ledger and would be the first thing to index if
engines with many thousands of cases become a hot path.
